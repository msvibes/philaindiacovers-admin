A `current_profile_role()` `SECURITY DEFINER` helper function (in the same migration) so the `covers` policies can check the caller's role without granting any authenticated user direct read access to the whole `profiles` table — same narrow-capability pattern as ADR-005's `verify_cover()`. Always keyed off `auth.uid()`, so it can only ever return the caller's own role.

**Real security bug found and fixed while verifying the above (same day, not part of the original T-04 scope):** confirming ADR-007's premise turned up that `anon`/`authenticated` had `TRUNCATE`, `REFERENCES`, `TRIGGER`, and `MAINTAIN` granted on `covers`, `profiles`, AND `postal_circles`, independent of anything any migration asked for. `TRUNCATE` does not evaluate RLS at all in Postgres, so no RLS policy could ever have stopped it — this is what made the grant genuinely worth fixing, not something T-04's own RLS work would have caught. Root cause: this project's baseline default ACL leaves both roles with these four privilege types by default on every table; "Automatically expose new tables" being off only suppresses the CRUD ones. Fixed via explicit `REVOKE` on the existing tables and on the default ACL going forward (`20260804180223_revoke_rls_bypassing_privileges.sql`, `20260804180432_revoke_maintain_privilege.sql`).

**Proven behaviorally both ways, not just inferred from grant listings — per the same rigor as the RLS integration tests and the secret-leak guardrail:** directly attempted `SET ROLE anon; TRUNCATE covers;` (and the same for `authenticated`) post-fix and got a real rejection — `42501: permission denied for table covers` — not just an ACL check. **Also directly tested the actual public attack surface** (a raw HTTP request with the real anon key against the REST API, not a SQL session) and confirmed PostgREST has no path to this at all, independent of grants: an unfiltered `DELETE` is refused outright ("DELETE requires a WHERE clause"), no raw-SQL RPC endpoint exists. **Corrected severity as a result**: this was a real, worthwhile defense-in-depth fix — an unnecessary grant that widens blast radius for any future RPC function or platform change — but not a live, exploitable hole via the documented public API the way the same-day framing first suggested. Both the direct proof and the corrected severity are in `docs/Threat-Model.md`'s row for this, not left as the original overstated framing.

**Storage bucket-level permissions are explicitly out of scope for all of the above — not yet reviewed at all.** Every fix above is Postgres/RLS-level. Supabase Storage is a separate permission system entirely (its own policies, not `covers`' RLS); the planned design (`docs/API-Integration-Contracts.md` §4: Admin-only writes, public read only for `verified` covers' images) hasn't been implemented or reviewed, since no image upload exists in the app yet. Flagged explicitly in `docs/Threat-Model.md` as its own scope note so today's Postgres-grant fixes don't get mistaken for having covered it — needs its own review once image upload is actually built.

## Known gotchas from recent sessions
- **`fetchCurrentRole()` (`src/lib/currentRole.ts`) is the one place to call `current_profile_role()` from the browser for UI routing/display — reuse it, don't call the RPC ad hoc.** It's UI-only by design: a stale or spoofed client-side role value can misroute the UI but can never grant real access, since RLS/`verify_cover()`/`requireRole()` all re-derive the role server-side independently regardless. Worth knowing why it works at all: `current_profile_role()` never got its own explicit `grant execute` the way `verify_cover()` did — it's reachable via RPC purely because Postgres grants `EXECUTE` on new functions to `PUBLIC` by default and nothing in this project's migrations has ever revoked that. Confirmed empirically, not assumed. If a future security pass ever locks down function-level default privileges (mirroring what already happened for table-level `TRUNCATE`/`REFERENCES`/`TRIGGER`/`MAINTAIN`), this RPC call — and every page guard built on it — would break; would need its own explicit `grant execute ... to authenticated` at that point.
- **`/import` and `/review` now live under `src/app/(app)/` (a Next.js route group), not directly under `src/app/` — URLs are unchanged, only file location.** Added for the logout button's shared header (`src/app/(app)/layout.tsx` + `src/components/AppHeader.tsx`). Any future authenticated page should go under this same group to get the header (and logout) for free rather than duplicating it — `/login` and the scaffold root page are deliberately outside it, since there's no session to log out of on either.
- **There was no logout anywhere until this session — worth remembering this class of gap can hide in plain sight.** T-06.5 built login; T-07 built a whole authenticated screen; neither task's scope (nor its Non-Goals) ever mentioned signing out, so nothing caught it until the user hit it themselves while manually testing. Worth a deliberate check on any future auth-adjacent task: does this add a capability that also needs an "undo" (logout, revoke, delete) with no obvious task currently covering it?
- **Not every Verifier/Admin-facing feature needs a Route Handler — confirm per-feature, don't default to the T-03/T-05 pattern (T-07).** Those two routes needed service-role for specific reasons (pre-auth RLS bypass; Storage writes with zero `authenticated` grant) that don't automatically apply elsewhere. If RLS already grants the caller's own role direct access, or the write goes through a `SECURITY DEFINER` function with its own role check, the browser's own authenticated client (`supabaseBrowser`) can call it directly — genuinely simpler and no less secure. T-07 (list via RLS, write via `verify_cover()` RPC) is the reference example.
- **`cover-images` Storage now has real `authenticated`-role read policies (T-07), not just `service_role` — reuse them, don't add a third mechanism.** `20260808153406_cover_images_review_read_policies.sql` mirrors `covers`' RLS shape: Admin reads any status, Verifier reads draft/flagged only. Public read for `verified`-only images (the consumer app's need, T-08/T-09) is still a distinct, unbuilt policy — don't assume T-07's policies already cover it.
- **`postal_circles` now actually has a grant + RLS policy (T-07) — it didn't before, despite being documented as "Public read" since T-01.** If a future authenticated/anon query against a table gets a flat "permission denied" (not zero rows), suspect a missing grant before suspecting RLS — check `information_schema.role_table_grants`, the same diagnostic that caught this. Any table created before `20260804175714_default_privileges_authenticated.sql` (2026-08-04) and lacking its own explicit grant is a candidate; `covers` got one in T-04, `postal_circles` didn't until now — worth a quick check if a similarly-old table is ever queried by a new authenticated code path for the first time.
- **Route Handler auth convention (T-06.5, ADR-008): Bearer token, not cookies.** `requireRole(request, role)` (`src/lib/requireRole.ts`) is what any future Admin/Verifier-gated Route Handler should call, the same way `current_profile_role()` is the one to reuse for RLS policies. The browser side is `authorizedFetch()` (`src/lib/authorizedFetch.ts`) — use it instead of raw `fetch` for any client-side call to a protected route. No `@supabase/ssr` in this repo; if a future task needs page-level (Server Component/middleware) auth gating rather than just API-route gating, that's a new decision, not an extension of this one — see ADR-008's accepted cost.
- **No trigger auto-creates a `profiles` row on Supabase Auth signup — confirmed absent, not assumed.** Anything that creates an `auth.users` row (the provisioning script, the integration tests' `createTestUser` helper) must also explicitly insert the matching `profiles` row itself, or the account is left with no role and every `requireRole()`/`current_profile_role()` check on it fails closed (403), not open.

Pre-confirms the account (`email_confirm: true`) — there's no unconfirmed-user/email-verification state anywhere in the back-office to handle, since there's no self-service signup at all.
