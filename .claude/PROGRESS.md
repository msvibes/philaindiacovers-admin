**Rollback/partial-failure reasoning, verified behaviorally, not just decided:** upload the image to Storage *first*, then insert the `covers` row referencing it — deliberately, not the other way around. This ordering means a failure only ever produces one of two states: nothing created (upload itself failed), or an orphaned Storage file with no DB reference (insert failed after a successful upload) — never a `covers` row whose `image_file` points at nothing, which would be worse (a "draft" entry a Verifier might open expecting an image that doesn't exist). On an insert failure, the just-uploaded file is deleted as best-effort cleanup — not a true atomic rollback (Storage and Postgres are different systems, can't share a transaction), so a second, simultaneous failure on the cleanup delete itself could still leave a stray file; accepted as a low-stakes leftover, not treated as needing a retry queue. **Verified for real**, not just reasoned about: temporarily revoked `service_role`'s `INSERT` grant on `covers`, ran a row through confirm-import, confirmed the image uploaded then the insert failed then the orphaned file was actually deleted (checked directly, not assumed), then restored the grant. Rows are processed independently (not one all-or-nothing transaction across the whole batch) — matches the per-row success/failure report `API-Integration-Contracts.md` §3 already specifies for the bulk-import function, not a new preference.

**T-04 needed two things beyond the policies themselves:**
1. A grant to `authenticated` on `covers` — per T-03's finding, this project's "Automatically expose new tables" setting suppresses default grants for `anon`/`authenticated` too, not just `service_role`. RLS alone filters rows on top of an existing grant; without it, every query would've failed outright instead of being properly row-filtered. **Design revised same-day**: originally scoped per-table (deliberately, not a blanket default-privileges fix), but confirmed — see **ADR-007** — that this project has "Enable automatic RLS" checked project-wide, so every future table gets RLS default-deny the moment it's created regardless of creation method. That makes a blanket `ALTER DEFAULT PRIVILEGES ... TO authenticated` just as safe as `service_role`'s fix was: `collection_items`, `wishlist_items`, `verification_audit_log`, and anything created later will be grant-covered AND RLS-locked-down automatically, not wide open until their own task remembers a grant. Switched to that approach (`20260804175714_default_privileges_authenticated.sql`); `covers`' own explicit grant stays too, since default privileges don't apply retroactively to tables that already existed. Deliberately **no** anon grant on `covers` — no anon-facing use case in the locked design, so anon should be refused outright by PostgREST, not silently filtered to zero rows.
2. A `current_profile_role()` `SECURITY DEFINER` helper function (in the same migration) so the `covers` policies can check the caller's role without granting any authenticated user direct read access to the whole `profiles` table — same narrow-capability pattern as ADR-005's `verify_cover()`. Always keyed off `auth.uid()`, so it can only ever return the caller's own role.

**Real security bug found and fixed while verifying the above (same day, not part of the original T-04 scope):** confirming ADR-007's premise turned up that `anon`/`authenticated` had `TRUNCATE`, `REFERENCES`, `TRIGGER`, and `MAINTAIN` granted on `covers`, `profiles`, AND `postal_circles`, independent of anything any migration asked for. `TRUNCATE` does not evaluate RLS at all in Postgres, so no RLS policy could ever have stopped it — this is what made the grant genuinely worth fixing, not something T-04's own RLS work would have caught. Root cause: this project's baseline default ACL leaves both roles with these four privilege types by default on every table; "Automatically expose new tables" being off only suppresses the CRUD ones. Fixed via explicit `REVOKE` on the existing tables and on the default ACL going forward (`20260804180223_revoke_rls_bypassing_privileges.sql`, `20260804180432_revoke_maintain_privilege.sql`).

**Proven behaviorally both ways, not just inferred from grant listings — per the same rigor as the RLS integration tests and the secret-leak guardrail:** directly attempted `SET ROLE anon; TRUNCATE covers;` (and the same for `authenticated`) post-fix and got a real rejection — `42501: permission denied for table covers` — not just an ACL check. **Also directly tested the actual public attack surface** (a raw HTTP request with the real anon key against the REST API, not a SQL session) and confirmed PostgREST has no path to this at all, independent of grants: an unfiltered `DELETE` is refused outright ("DELETE requires a WHERE clause"), no raw-SQL RPC endpoint exists. **Corrected severity as a result**: this was a real, worthwhile defense-in-depth fix — an unnecessary grant that widens blast radius for any future RPC function or platform change — but not a live, exploitable hole via the documented public API the way the same-day framing first suggested. Both the direct proof and the corrected severity are in `docs/Threat-Model.md`'s row for this, not left as the original overstated framing.
