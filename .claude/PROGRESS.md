- **The user's first real Google sign-in (`krutimlogic@gmail.com`, brand-new account, default `collector` role) surfaced something much bigger than the UX question that prompted it — see `docs/Threat-Model.md`'s new Elevation-of-Privilege row for the full writeup, summarized here:**

  1. **`verify_cover()`'s role guard was NULL-unsafe — a real, exploitable-by-accident-only bug, fixed with `IS DISTINCT FROM`.** The original guard, `if current_profile_role() <> 'verifier' then raise exception`, silently passed any caller with no `profiles` row at all, because `NULL <> 'verifier'` is NULL in SQL and PL/pgSQL treats a NULL `IF` condition as false. **Proven empirically before and after, not assumed**: before the fix, a throwaway account in that exact orphaned state got past the guard and was only stopped because `covers.verified_by references profiles(id)` had nothing to reference — an accidental backstop, surfaced as a raw FK-violation error, not the intended rejection message. After the fix (`20260811182101_fix_verify_cover_null_role_guard.sql`), the identical scenario produces the correct `"Only the Verifier role may call verify_cover()"` message instead, confirmed via a new regression test that asserts the message text explicitly (not just "an error occurred") and that it does *not* mention a foreign key.

  2. **Audited the rest of the codebase for the same `<>`-against-nullable-value pattern — this was the only instance.** Every RLS policy (`covers`, `verification_audit_log`, `cover-images` Storage) and the FR-24 correction-reset trigger use `=` in a *permit-if-true* / *fire-if-true* context. **Why that's structurally safe and the `<>` guard wasn't, precisely**: Postgres RLS treats a NULL `USING`/`WITH CHECK` result the same as FALSE — access is granted only when the expression is TRUE, so a NULL role naturally denies by default. `verify_cover()`'s guard ran the opposite direction — access was granted *by default*, and only blocked when the reject-condition was TRUE — so a NULL result (which is neither TRUE nor FALSE) fell through to the *permissive* default instead of the restrictive one. The general lesson isn't "always use `IS DISTINCT FROM`" so much as "a default-deny, explicitly-grant gate (RLS's shape) is structurally robust against NULL; a default-allow, explicitly-reject gate is not, even once the specific comparison is made NULL-safe."

  3. **Root cause closed, not just the symptom — `handle_new_user()` trigger (`20260811182123_auto_create_profile_on_signup.sql`).** The real reason `current_profile_role()` returned NULL at all: no trigger has ever existed to create a matching `profiles` row on signup, so the schema's stated `role text not null default 'collector'` never actually applied to a self-service account — that default only fires on an INSERT, and nothing ever performed one. Standard Supabase pattern: a `SECURITY DEFINER` function on `auth.users AFTER INSERT` that inserts `(new.id, 'collector')` into `profiles`. **Verified empirically**: a fresh throwaway signup immediately got a `profiles` row with `role = 'collector'`, and `current_profile_role()` correctly resolved to `'collector'` for it (not NULL) afterward.

## Known gotchas from recent sessions
- **Every `auth.users` INSERT now auto-creates a matching `profiles` row (`role = 'collector'`) via `handle_new_user()` — any code that creates a user and then writes `profiles.role` must `upsert`, not `insert`, or it hits a duplicate-key conflict.** Already fixed everywhere this applied as of 2026-08-11 (`scripts/provision-user.mjs`, `src/lib/testHelpers/createTestUser.ts`) — but if a new script or test ever creates a user via `admin.auth.admin.createUser()` and separately sets their role, remember this trigger fires first.
- **`covers.image_file` is `NOT NULL` as of 2026-08-12 — any test/script that seeds a `covers` row directly (not through the real import flow) must supply one, or the insert fails.** `verifyCover.integration.test.ts`, `coversRls.integration.test.ts`, `reviewQueue.integration.test.ts`, and `check-duplicate-covers/route.integration.test.ts` were all fixed for this. The two tests that insert specifically to prove RLS rejects it (Verifier/Collector, `coversRls.integration.test.ts`) didn't need fixing — their assertions are generic ("an error occurred"), correct regardless of which constraint actually fires first.
- **New rule for any future SQL guard written as "reject if X" rather than "permit only if X": use `IS DISTINCT FROM`, not `<>`/`!=`, whenever X could ever be NULL.** `NULL <> anything` is NULL in SQL, and PL/pgSQL treats a NULL `IF` condition as false — so a naive `<>`-based reject-guard silently *passes* a NULL value instead of rejecting it, the opposite of the intended default. This bit `verify_cover()` for real (found via a genuine Google sign-in, fixed 2026-08-11 — see `docs/Threat-Model.md`'s Elevation-of-Privilege row for the full writeup) and was only accidentally harmless there due to an unrelated FK constraint. RLS policies don't have this problem because they're structured the opposite way — "permit only if X is TRUE" — and Postgres already treats a NULL policy result as deny; that's the safer general shape (default-deny, explicit-grant) to prefer over "default-allow, explicit-reject" even when the specific comparison is fixed.
- **`fetchCurrentRole()` (`src/lib/currentRole.ts`) is the one place to call `current_profile_role()` from the browser for UI routing/display — reuse it, don't call the RPC ad hoc.** It's UI-only by design: a stale or spoofed client-side role value can misroute the UI but can never grant real access, since RLS/`verify_cover()`/`requireRole()` all re-derive the role server-side independently regardless. `current_profile_role()` now has its own explicit `grant execute ... to authenticated` (`20260810234304_grant_execute_current_profile_role.sql`), matching `verify_cover()`'s pattern — it was initially reachable only via Postgres' unrevoked default `PUBLIC` execute grant (caught and fixed before merge, same fragile-default category as T-03/T-04's earlier grant findings), so this is now a deliberate, documented decision, not an accident of what nobody's revoked yet.
