**T-04 needed two things beyond the policies themselves:**
1. A grant to `authenticated` on `covers` — per T-03's finding, this project's "Automatically expose new tables" setting suppresses default grants for `anon`/`authenticated` too, not just `service_role`. RLS alone filters rows on top of an existing grant; without it, every query would've failed outright instead of being properly row-filtered. **Design revised same-day**: originally scoped per-table (deliberately, not a blanket default-privileges fix), but confirmed — see **ADR-007** — that this project has "Enable automatic RLS" checked project-wide, so every future table gets RLS default-deny the moment it's created regardless of creation method. That makes a blanket `ALTER DEFAULT PRIVILEGES ... TO authenticated` just as safe as `service_role`'s fix was: `collection_items`, `wishlist_items`, `verification_audit_log`, and anything created later will be grant-covered AND RLS-locked-down automatically, not wide open until their own task remembers a grant. Switched to that approach (`20260804175714_default_privileges_authenticated.sql`); `covers`' own explicit grant stays too, since default privileges don't apply retroactively to tables that already existed. Deliberately **no** anon grant on `covers` — no anon-facing use case in the locked design, so anon should be refused outright by PostgREST, not silently filtered to zero rows.
2. A `current_profile_role()` `SECURITY DEFINER` helper function (in the same migration) so the `covers` policies can check the caller's role without granting any authenticated user direct read access to the whole `profiles` table — same narrow-capability pattern as ADR-005's `verify_cover()`. Always keyed off `auth.uid()`, so it can only ever return the caller's own role.

**Real security bug found and fixed while verifying the above (same day, not part of the original T-04 scope):** confirming ADR-007's premise turned up that `anon` — the fully public key — had `TRUNCATE`, `REFERENCES`, `TRIGGER`, and `MAINTAIN` granted on `covers`, `profiles`, AND `postal_circles`, independent of anything any migration asked for. `TRUNCATE` does not evaluate RLS at all in Postgres, so this was a live, currently-exploitable way to wipe any of those tables regardless of any RLS policy — not hypothetical, not something T-04's own RLS work could have caught, since RLS is irrelevant to `TRUNCATE`. `authenticated` had the same four privileges too. Root cause: this project's baseline default ACL leaves both roles with these four privilege types by default on every table; "Automatically expose new tables" being off only suppresses the CRUD ones. Confirmed via `pg_default_acl`/`information_schema.role_table_grants`, fixed immediately via explicit `REVOKE` on the existing tables and on the default ACL going forward (`20260804180223_revoke_rls_bypassing_privileges.sql`, `20260804180432_revoke_maintain_privilege.sql`), re-verified clean, all 23 tests still passing. Documented as an addendum to ADR-007 and a new Threat-Model.md row.
