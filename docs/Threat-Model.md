# PhilaIndiaCovers — Threat Model (Lightweight STRIDE)

Using Microsoft's STRIDE framework (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) — scoped realistically to a solo-built, ~100-user niche app, not enterprise-grade paranoia. Each row: is this a real risk here, and if so, what already handles it (per the locked design) versus what's still genuinely open.

> 📚 **Learning note:** STRIDE is a categorization checklist, not a magic detector — it works by forcing you to ask "could this category of attack happen to us?" for each of the six letters, one at a time, rather than trying to imagine every possible attack unassisted. Most real threat models (including this one) find that most categories are either "not really applicable at our scale" or "already handled as a side effect of the normal design" — the value is in systematically checking, not in every row producing a scary finding. A threat model with zero findings might mean nothing was actually reviewed; one with fifty findings for a 100-user hobby app probably means the reviewer lost the scoring/calibration for the system's actual size.

| Threat | Real risk here? | Mitigation |
|---|---|---|
| **Spoofing** — someone impersonates another collector | Low — no financial transactions, no messaging between users to spoof | Supabase Auth handles identity; account-linking (FR-26) is deliberately restricted to same-verified-email, not spoofable |
| **Spoofing** — someone impersonates the Admin/Verifier role | **Real, worth care** | `profiles.role` is server-side, never client-settable. **As of T-04**, `covers`' RLS policies check role via `current_profile_role()`, a `SECURITY DEFINER` helper keyed off `auth.uid()` — never a client-supplied claim. `verify_cover()` (T-06) will use the same non-spoofable pattern once built |
| **Tampering** — a Collector edits another user's Collection/Wish List | Real, **not yet implemented** — `collection_items`/`wishlist_items` don't exist yet | Planned: RLS `own_rows_only` policy (§4 of the LLD) — enforced at the database, not the UI, same pattern as T-04's `covers` policies |
| **Tampering** — a Verifier edits cover metadata directly | Real — **now implemented and tested (T-04)**, previously just the intended design | ADR-005 — no direct write grant/policy exists for this role on `covers` at all. Verified live: Verifier UPDATE/DELETE attempts silently affect 0 rows, INSERT raises an explicit RLS-violation error — covered by `src/lib/coversRls.integration.test.ts` (9 tests, all three roles), not just asserted |
| **Tampering** — bulk-import CSV contains malicious content (e.g. formula injection in a spreadsheet cell) | Real — **now resolved (T-02)**, not open | `sanitizeCsvCell()` (`src/lib/sanitizeCsvCell.ts`, Admin repo) strips leading whitespace and `=`/`+`/`-`/`@` in a loop until stable, applied to every field via Papa Parse's `transform` option. Hardened through review to also catch a leading-space bypass and null/undefined crash risk found during implementation. Covered by 8 passing Vitest unit tests — this is now a tested, enforced control, not a stated intention |
| **Repudiation** — a Verifier denies having flagged/verified an entry | Real, directly prevented | `verification_audit_log` records who/what/when/reason for every action, written atomically with the status change |
| **Information Disclosure** — a Collector sees another collector's personal Collection data | Real, **not yet implemented** — `collection_items`/`wishlist_items` don't exist yet | Planned: RLS `own_rows_only`, same pattern as T-04's `covers` policies once those tables exist |
| **Information Disclosure** — Draft/Flagged (unverified) covers leak to collectors before review | Real — **now implemented and tested (T-04)**, previously just the intended design | RLS restricts Collector SELECT to `verification_status = 'verified'` only. Verified live: a Collector-role client sees only the `verified` test row, not `draft`/`flagged` ones — `src/lib/coversRls.integration.test.ts` |
| **Information Disclosure** — Supabase service-role key exposed in client code | Real — **partially resolved (T-03)**, one piece still open | `scripts/check-no-secret-leak.mjs` (Admin repo, wired into `npm run build` via `npm run check:secrets`) greps git-tracked files and the built client bundle for the key pattern; verified to actually fail on a staged real leak, not just pass on clean input. Layered alongside Next.js's own `NEXT_PUBLIC_`-only client exposure and a `server-only` import guard on the admin Supabase client. **Still open:** not yet wired into an actual CI pipeline — no GitHub Actions workflow exists in either repo yet (ADR-006, Session 7) — so this only protects local builds today, not PRs from elsewhere |
| **Information Disclosure / Elevation of Privilege** — `/api/check-duplicate-covers` AND `/api/confirm-import` (Admin repo, T-03/T-05) have no access control | Real, currently **open** — found during T-03, not anticipated by this original review. **T-04 (2026-08-04) deliberately did not close this** — RLS/grants are a database-level control, and this gap is application-level (no session to check). **T-05 (2026-08-05) adds a second, more serious instance**: `/api/confirm-import` doesn't just read data like the T-03 route, it *writes* `covers` rows and uploads to Storage — meaning anyone who finds this endpoint today can create arbitrary catalogue entries and upload arbitrary files, not just enumerate existing data | None yet. No auth exists anywhere in either app before this point, so neither route can be gated to a role yet. **Both now have an assigned owner: T-06.5** (Admin/Verifier auth, added to `docs/AI-Agent-Implementation-Brief.md` once it became clear no task in the original decomposition ever built login at all) |
| **Tampering / Denial of Service** — `anon`/`authenticated` had `TRUNCATE` (and `REFERENCES`/`TRIGGER`/`MAINTAIN`) granted on `covers`, `profiles`, and `postal_circles` at the Postgres level | Real over-privilege, genuinely fixed same-day (T-04, 2026-08-04) — but **corrected severity assessment**: not actually reachable through the documented public API, so "an attacker could wipe the table via the anon key" (this row's original framing) overstated it | `TRUNCATE` does not evaluate RLS at all in Postgres — no RLS policy could ever have stopped this at the SQL level, which is genuinely why the grant itself mattered and was worth fixing regardless of reachability. Root cause: this project's baseline default ACL (independent of any migration) left both roles with these four privilege types; "Automatically expose new tables" being off only suppresses the CRUD ones. **Proven, not inferred, both ways:** before the fix, confirmed via `pg_default_acl`/`information_schema.role_table_grants`; after the fix, directly attempted `SET ROLE anon; TRUNCATE covers;` (and the same for `authenticated`) and confirmed real rejection — `42501: permission denied for table covers` — not just a grant-listing check. **Also directly tested the actual public attack surface** (the anon key over the real REST API, not a raw SQL session) and confirmed PostgREST has no path to this regardless of grants: an unfiltered `DELETE` is refused outright ("DELETE requires a WHERE clause"), and no raw-SQL RPC endpoint exists. So this was a real, worthwhile defense-in-depth fix (unnecessary grant, wider blast radius for any future RPC function or platform change) — not a live, exploitable hole via the documented API the way the same-day framing first suggested |
| **Denial of Service** — a malicious actor floods signups or bulk-import requests | Low — niche ~100-user app, not a public high-value target | Supabase's own platform-level rate limiting is the realistic first line of defense at this scale; no custom rate-limiting layer justified for v1 |
| **Elevation of Privilege** — a Collector account gets `role = 'admin'` somehow | Real, directly prevented | `profiles.role` is only ever set server-side (manually, for the two known Admin/Verifier accounts) — no user-facing flow ever writes this column |
| **(Scope note, not a scored row)** — Supabase **Storage** bucket-level permissions | **Partially built (T-05), full design still not reviewed** | The `cover-images` bucket now exists — private, with no `anon`/`authenticated` policies on `storage.objects` at all, so only `service_role` (via `BYPASSRLS`, same as table RLS) can touch it. That's sufficient for T-05's own need (server-side upload during confirm-import) and is a genuinely locked-down starting point, not an open one. **Still not implemented or reviewed**: the full locked design from `API-Integration-Contracts.md` §4 — public read access for images belonging to `verified` covers only, which needs its own `storage.objects` RLS policy joining against `covers.verification_status`, a real design question distinct from anything built so far. Needed once the consumer app (T-08/T-09) actually has to display images to collectors, not before |

## Open Items Remaining From This Review

**Service-role-key exposure guardrail — local check built (T-03), CI wiring still open.** `scripts/check-no-secret-leak.mjs` exists and runs on every local build, verified to actually catch a leak rather than just assumed to work. What's still missing is running it (and lint/typecheck/tests generally) as an actual CI gate on every PR — no GitHub Actions workflow exists in either repo yet. That's ADR-006's decision, not yet built.

**`/api/check-duplicate-covers` AND `/api/confirm-import` have no access control — found during T-03/T-05, new since this document was first written.** A real, currently-exploitable gap (see the table row above), not just a theoretical one — T-05's route is the more serious of the two, since it writes data and uploads files, not just reads. Needs to be closed before this goes past local development — now scheduled as **T-06.5** rather than left ownerless.

*(The CSV-injection sanitization item that originally appeared alongside the service-role-key item was resolved during T-02 — see the Tampering row above. This document is updated to reflect that, rather than left stating a risk that no longer exists.)*

Everything else in this table reflects protections already designed in, not new work — this review's value was mostly *confirming* the existing design holds up under a structured threat lens, plus catching genuine, still-open gaps as they're found (both at initial review time, and as new ones surface during actual implementation, like the two above).
